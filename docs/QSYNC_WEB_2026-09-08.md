# qSync 웹 구현 기록

작성일: 2026-09-08
브랜치: `feat/qsync-web-20260908`
기준: `121d042` 및 root가 통합한 B 계약 DTO

이 변경은 기존 한국어 동기화 관리 화면과 수동 폴더 연결을 유지하면서
키 기반 폴더 공유 흐름을 추가한다. overview/folders의 기본 동작은 `폴더
공유`와 `키로 연결`이며, 기존 `폴더 추가`는 `고급 연결` 안에서 계속
사용한다. 화면은 owner의 공유·pending 목록을 실제 snapshot 데이터로
표시하고, 등록된 멤버 수를 온라인 수로 추정하지 않는다. `active_peer_count`
와 현재 연결 장치를 별도 표시하며 전송량은 bytes, 속도는 bytes/sec이다.

## 계약과 경로

웹 API는 `/api/v1/shares` 이하의 B Manager 경로를 사용한다.

- 키 body의 `key`는 route에서 Manager 입력 `encoded_key`로 전달한다.
- share/invitation ID는 URL에서 percent-encode하고, 서버는 32바이트 소문자
  hex 64자로만 받는다. `member_id`와 `request_id`는 불투명 문자열 경계를
  적용한다.
- `preview`는 로컬 서명·만료를 확인하고, `validate`는 owner 온라인 발급
  기록을 확인한다. 사용자는 한 번의 `키 확인` 동작으로 두 단계를 거친다.
  offline이면 확인되지 않은 상태를 명시한 뒤 폴더 선택과 pending join을
  허용한다. invalid/revoked 키는 join하지 않는다.
- 가입은 이 웹 콘솔을 실행하는 장치의 authenticated `/browse`에서 고른
  서버 폴더를 사용한다. API 응답 유실 재시도는 입력 fingerprint가 같을 때
  같은 `request_id`를 재사용하며 입력이 바뀌면 새 ID를 만든다. 세대와
  mounted guard가 늦은 응답이 현재 화면을 덮지 않게 한다.
- 오류는 `error_code`의 고정된 한국어 문구만 화면에 보여준다. 내부 오류
  chain, 경로, ID 전체, bearer는 사용자 오류·activity·URL·SSE에 넣지 않는다.

## 비밀과 상태 경계

발급된 raw key는 발급 응답에서 한 번만 표시하고 React memory에만 둔다.
복사 뒤 목록을 다시 조회해 키를 재노출하지 않는다. modal close, 성공,
취소, 만료, logout 시 상태와 operation tracker를 지운다. localStorage,
sessionStorage, URL, console, SSE에는 키를 쓰지 않으며 스크린샷 검증 시
`data-sensitive="share-key"` 영역을 마스킹한다. 만료 timer는 브라우저의
약 24.8일 한계를 넘지 않도록 제한된 재예약 후 실제 Unix seconds를 다시
확인한다. 관리형 timestamp는 Unix seconds이므로 표시할 때만 milliseconds로
변환한다.

상태 값은 계약의 8개(`waiting`, `offline`, `initial_sync`, `complete`,
`conflict`, `revoked`, `error`, `paused`)를 그대로 표시한다. `pending`은
가입·멤버 철회의 진행 상태로, 결과의 `completion`이 명시적으로
`complete`일 때만 완료로 표시한다. member 철회가 pending이면 “연결 종료
확인 중”으로 남기고 재조회/동일 요청 재시도를 안내한다. 네트워크 분할에서
owner handler drain만으로 전역 전송 종료를 주장하지 않는다. key 철회는
신규 가입을 막는 즉시 완료 경계이며 이미 전달된 파일을 회수하지 않는다.
공유 연결 해제는 managed 연결·등록만 정리하고 로컬 파일과 복구 데이터는
유지한다.

## 담당 파일과 완료 조건

웹 UI/API/테스트는 `web/src/App.tsx`, `api.ts`, `types.ts`, `share.tsx`,
`share.test.tsx`, `components.tsx`, `styles.css`에 있다. HTTP adapter와
경계 테스트는
`crates/deltaweave-web/src/{share_routes.rs,routes.rs,routes/tests.rs}`가
담당한다. 새 route는 기존 protect middleware 아래에 있으며 login, Host,
same-origin Origin, Sec-Fetch, CSRF, 64 KiB 제한을 그대로 통과해야 한다.

완료 판정에는 다음이 모두 필요하다.

1. B Manager의 실제 메서드와 error classifier가 web worktree에 연결되어
   `DELTAWEAVE_REQUIRE_WEB_ASSETS=1 cargo test/clippy -p deltaweave-web`
   가 통과한다. 현재 이 문서 작성 시점에는 B 구현이 별도 worktree에서
   진행 중이므로 Rust 통합 결과를 완료로 표시하지 않는다.
2. 아래 npm 검사와 API/UI 경계 테스트가 통과한다.
3. 실제 browser에서 1440/390 viewport, Tab/Escape/focus 복귀, long key,
   clipboard 실패, console/pageerror 및 masked screenshot을 확인한다.
4. F 단계에서 분리된 owner/RO/RW 프로세스, Windows native, Internet/N0
   전송과 실제 worker join/resume를 검증한다. 로컬 프로세스 수를 물리적
   3기기 증거로 세지 않는다.
